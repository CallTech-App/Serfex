Optimization suggestions now also look at PHP-FPM, Nginx, PostgreSQL, Memcached and the sites' Redis instances, and if you want they can apply small changes themselves. A WordPress site's staging copy no longer sends email to customers; the Laravel health card no longer shows 301 on a www redirect.

- **PHP-FPM and OPcache suggestions:** Services → PHP 8.x (PHP-FPM) → **Suggestions** (an "Optimization suggestions" button on the PHP version page). Every PHP version is measured every hour: how full OPcache memory is, how many times it filled up and was flushed, the hit rate, the number of cached files; whether each site's PHP workers hit their limit, and whether there are workers sitting idle.
  - If OPcache memory is over 90% or has filled up and been flushed, it is grown (used × 1.3, in steps of 128/192/256/384/512/768/1024 MB). Interned strings memory and the file count are grown too when they are about to fill up. If OPcache is off, turning it on is suggested.
  - If a site's workers hit their limit, worker count × 1.5 is suggested; the memory impact is calculated from that site's average memory per worker. For quiet sites running "Kept ready" or "Fixed number", "On demand" is suggested, which frees the memory of idle workers.
  - OPcache values are written to the version's php.ini defaults and worker settings to the site's PHP settings (the same places you change by hand). PHP-FPM is reloaded: running requests complete, and OPcache fills up from scratch. It is watched for 30 minutes and can be undone for 7 days.
  - `opcache.validate_timestamps` is never turned off: while it is off, newly deployed code does not run.
  - An OPcache value changed by hand (PHP versions) or a site's worker setting (PHP & Web Server) is locked; the optimizer makes no suggestion for it.
  - To read OPcache, a small pool (`serfex_probe`) that only root can reach and that starts a worker on request is added to every PHP version. PHP-FPM is reloaded once at the first measurement.
- **New level: Apply small changes by themselves** (Services → Optimization). Suggestions that change a value by at most 50% and fit in the memory budget are applied automatically, at most one per service per day. Those that reload PHP-FPM wait for the maintenance window. Large changes, on/off changes and suggestions that were rolled back in the last 7 days still wait for you. What was done automatically appears in the list as "Serfex (automatic)". The default level did not change: Suggestions only.
- **Suggestions for Nginx, PostgreSQL, Memcached and the sites' Redis instances** (Services → Optimization; a **Suggestions** tab on each service's page, and for Redis, Services → Optimization → Redis (site caches)). All are measured every hour.
  - **Nginx:** if the error log said "worker_connections are not enough" in the last 7 days, connections per worker are doubled (768 → 2048); if needed, the workers' open file limit (`worker_rlimit_nofile`) is raised too. If "Too many open files" is seen, only the file limit is raised. If `worker_processes` is lower than the number of cores, "auto" is suggested. Nginx is reloaded, and connections are not dropped.
  - **PostgreSQL:** if the data does not fit in the cache (`shared_buffers`) and reads go to disk, the cache grows to 1.25 times the data, at most a quarter of memory; this restarts PostgreSQL (connections drop for a few seconds), so the Apply dialog opens with the maintenance window. If queries write temporary files to disk, `work_mem` is doubled (at most 64 MB). `effective_cache_size` becomes half of memory. On SSD/NVMe, `random_page_cost` becomes 1.1 and `effective_io_concurrency` 200. Values are written to `conf.d/zz-serfex-tuning.conf` and checked by PostgreSQL.
  - **Memcached:** if it is full and evicting items, memory is doubled; if it refused connections, the connection limit is doubled. Memcached restarts and the cache is emptied.
  - **Sites' Redis instances:** if a Laravel application's Redis went over 80% of its limit, or filled up and refused writes, its limit goes up to 1.5 times peak usage (for example 128 → 192 MB). The new limit is given to the running Redis without a restart.
  - The Services → PostgreSQL and Memcached pages got a **Settings** tab. A value changed by hand there is locked, and the optimizer makes no suggestion for it (the same goes for Nginx).
  - The automatic level never makes changes that need a restart (the PostgreSQL cache, Memcached) on its own.
- The **memory budget** now calculates the suggestions of all services together and shows PostgreSQL separately; PHP-FPM's share no longer counts OPcache's shared memory again for every worker.
- The titles of applied changes now appear in English in the English interface too.
- **The Laravel health check follows redirects:** Laravel → Overview → the Health card no longer shows 301 when the site redirects to `www.` or to the bare address; it follows the redirect on the same server and shows the real result of the `/up` page. For sites that redirect to another domain, it says where the redirect goes. Pressing **Check now** shows "Checking…", and the result shows the time of the check.
  - The same fix applies to the post-deployment health check: on sites whose preferred address is `www.`, deployments are no longer counted as failed and rolled back because of the 301.
- **WordPress staging copy:** a new **Staging copy** row on the WordPress page. On a site without a copy, **Create a staging copy** (opens Copy site: `staging.<domain>`, a database copy, wp-config and addresses replaced, 7-day Undo after publishing to live). On a site with a copy, the copies are listed; the copy's own WordPress page shows which site it is a copy of and a "Refresh from source, publish to live or set up" link.
  - **Email and WP-Cron are off by default on the copy.** Because the copy runs on the live site's data, order, password reset and newsletter emails could go to real customers, and scheduled tasks such as subscription payments could run. Serfex puts a small plugin on the copy (`wp-content/mu-plugins/serfex-staging.php`): emails are not sent (WordPress counts them as sent, and they are written to the PHP error log), WP-Cron tasks do not run, and the dashboard shows a "This is a staging copy" notice. Both can be turned on and off separately from the Copy site page (with Undo).
  - When publishing to live, the plugin is removed from the live site; even if it somehow stays, it works only on the copy's address and does nothing on the live site. If the copy's name is changed, the plugin is rewritten for the new name.
  - On copies created earlier, this restriction takes effect at the next "Refresh from source" or when a setting is changed.
  - Copy site was tried end to end for the first time with a real WordPress 6.8.3, MariaDB 10.11, Nginx and PHP-FPM 8.3: copying, address replacement (posts and serialized settings included), the email and WP-Cron restriction, and publishing to live.
