Laravel deployments with "Back up the database before every deployment" no longer stop with "Access denied; you need the RELOAD or FLUSH_TABLES privilege".

- **Pre-deployment database backup:** on MySQL servers with GTIDs on (`gtid_mode=ON`), or where an option file set `source-data`/`lock-all-tables` for `mysqldump`, the dump asked for `FLUSH TABLES WITH READ LOCK`, which the site's own database user may not run (error 1227). The deployment then stopped at 0 seconds. The dump now reads no option files (`--no-defaults`) and, with MySQL's `mysqldump`, leaves out the GTID line (`--set-gtid-purged=OFF`). It still takes a consistent InnoDB snapshot (`--single-transaction`) with only the site user's rights, so no extra MySQL privilege has to be granted by hand. MariaDB is not affected and is dumped as before.
- **Restoring these backups:** a dump made on a GTID server no longer contains `SET @@GLOBAL.GTID_PURGED`, which the site's database user could not restore either.
- **When the backup still fails** (a full disk, for example), the deployment still stops before anything changes, and the message now says that nothing was deployed and that unticking "Back up the database before every deployment" under Deployments deploys without a backup.
- The same applies to the database part of the Laravel page's manual and scheduled backups.
