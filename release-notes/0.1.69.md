Domains can now be managed in Cloudflare (records are written to Cloudflare and synced both ways, certificates are issued behind the proxy too, and the visitor's real IP is visible), and Serfex now opens every site once a minute and reports a site that does not respond, a failed or rolled-back deployment, a scheduled task failing again and again, and a queue worker that keeps crashing.

- **Cloudflare accounts:** Domains & DNS → **Cloudflare**. An API token is connected for each Cloudflare account; **Check token** shows what the token can do (DNS, SSL mode, adding domains) before it is saved. The token is stored encrypted and never shown again. More than one account can be connected (your own account and a customer's account, for example). Defaults:
  - **Cloudflare proxy:** site addresses (the domain, `www` and the site's other names) are written with the orange cloud; mail, webmail, FTP and panel addresses always stay DNS only. If you prefer, none of them go through the proxy and you turn it on per record.
  - **SSL mode:** once the site's Let's Encrypt certificate is ready, the zone's SSL/TLS mode is set to **Full (strict)** (once; if you change it in Cloudflare later, it is left alone). Because Flexible mode causes an endless loop with Serfex's HTTPS redirect, the zone page shows a warning and a **Set Full (strict)** button.
  - **Laravel deployment:** after a successful deployment the site's pages are purged from the Cloudflare cache (off by default).
- **Add site:** when the domain is typed, it is looked up in the connected Cloudflare accounts; if it is found, **Cloudflare · found in the … account** comes selected and what will change in Cloudflare is shown beforehand (the old server's A record → this server). The site's address records are written, and every other record (mail hosted elsewhere, verification records, subdomains) stays as it is and is imported into Serfex. The **Visitors come through Cloudflare (proxy)** box comes from the default. A domain that is not in Cloudflare can be added to the chosen account (**Add to Cloudflare**); then the name servers at the registrar are changed to Cloudflare's. If Cloudflare refuses something, the site is still created and DNS stays on this server.
- **Existing zones:** **Connect DNS to Cloudflare** on the zone page. The records on both sides are compared, and only the ones that differ are listed, each with a choice (write Serfex's / keep Cloudflare's / import into Serfex / delete from Cloudflare…). **Settings → Move DNS back to this server** goes back at any time; records in Cloudflare are not touched.
- **Two-way sync:** records can be changed from Serfex or from the Cloudflare dashboard. Serfex syncs every 5 minutes (and right after every change in the panel); if the same record changes in both places, Serfex's version wins. A record deleted on one side is deleted on the other, and a new record is added to the other side. Record types Serfex does not keep (HTTPS, SVCB…) and Cloudflare's own NS/SOA records are not touched. A record Cloudflare refuses does not stop the others, and the error appears on the zone page. For a zone in Cloudflare, this server's DNS (PowerDNS) stops serving it.
- **Zone page:** Cloudflare status, name servers (while waiting, the old name servers at the registrar too), SSL mode, DNSSEC and what the last sync changed; a **Cloudflare** column in the record table (Proxied / DNS only, click to switch; the TTL of proxied records is Auto), a proxy box in the record dialog, **Sync now**. If the name servers have not changed yet, a "Cloudflare is waiting for this domain" warning shows Cloudflare's two name servers, ready to copy. The Settings tab has the Cloudflare account, the SSL mode choice and turning DNSSEC on/off in Cloudflare (with the DS record).
- **Domain list:** a new **DNS** column (Cloudflare · account / This server) and a "Waiting for name servers" label.
- **Certificates behind Cloudflare:** certificates of sites whose DNS is in Cloudflare are issued with DNS validation: the agent writes the `_acme-challenge` records to Cloudflare with the zone's token, waits until Cloudflare's name servers answer (at most 90 seconds), then deletes them. It works with the orange cloud on as well; wildcard certificates can be issued too. While Cloudflare's name servers are awaited, the certificate shows "Waiting for DNS" and is requested as soon as the zone becomes active.
- **Purge Cloudflare cache:** Site → Cache and speed. If the zone holds only this site, the whole cache is purged; otherwise only the site's addresses.
- **The visitor's real IP:** for requests from Cloudflare's addresses, Nginx takes the visitor's address from the `CF-Connecting-IP` header (`/etc/nginx/conf.d/serfex-realip.conf`). Logs, statistics, the WAF, IP blocks and Laravel's `request()->ip()` see the real visitor. Cloudflare's address list is updated once a week (and once right away at the update).
- **Cloudflare addresses are never blocked:** the panel, Serfex AI and the agent refuse to block Cloudflare's addresses, and Fail2ban ignores them (all visitors of proxied sites come from these addresses). Blocked addresses are refused by Nginx even when they come through Cloudflare (`/etc/nginx/conf.d/serfex-blocked.conf`).
- **Site uptime:** Serfex opens every site once a minute at the address a visitor uses (the preferred name, HTTPS, Cloudflare included; 10-second timeout; on Laravel the health path `/up`, otherwise `/`). A failed connection, a timeout and a 5xx (Cloudflare 52x errors by name) count as down; a 4xx such as 404 counts as a response. A failed check is also tried from the server itself and the reason is given ("Also failed when tried from the server: HTTP 502. PHP-FPM may not be responding." or "the problem is on the DNS, Cloudflare or network side"). After two failed checks in a row an outage is opened and administrators are notified right away; when the site recovers, "Resolved" follows. Suspended sites, Laravel applications in maintenance mode and new sites that have never responded (DNS not pointed yet) are not reported.
- **Uptime card:** Site → Overview. The last 24 hours in 15-minute bars, 24-hour and 30-day uptime, average response time, the checked address and recent outages (with their reasons). **Set up** changes the checked path or turns monitoring off. In the site list a site that is down shows a **Not responding** label. Records are kept for 90 days.
- **New notification types** (Settings → Notifications, all on by default): **Sites** (a site that does not respond), **Deployments** (a Laravel/Git deployment that failed or was rolled back by the health check; for 24 hours or until a successful deployment), **Scheduled tasks** (when a task, or a task in the Laravel scheduler, fails 3 times in a row), **Queues and processes** (when a queue worker or a Horizon/Reverb/Octane process crashes and restarts 5 times in 10 minutes, or stops; a clean exit with `--max-jobs`/`--max-time` does not count).
- **Overview:** these problems appear at the top of the Problems list, with a button to the relevant page.
